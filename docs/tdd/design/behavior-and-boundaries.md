# 행동과 경계값 테스트

> AC로 받아들일 동작을 정하고 TC로 입력·행위·기대 결과를 구체화해 요구와 불변식을 검증한다.

- **기준:** AC는 수용 기준, TC는 그 기준을 확인할 테스트 케이스다.
- **선택:** 정상·빈 값·경계·중복·동시성·실패를 대표하는 사례를 고른다.
- **검토:** 테스트 수나 커버리지보다 요구사항과 기대값의 일치를 확인한다.

## 설명

AC(Acceptance Criteria, 수용 기준·인수 기준)는 기능을 받아들일 조건이다. TC(Test Case)는 사전 조건, 입력, 행위, 기대 결과와 필요한 사후 조건을 구체화한다. 하나의 AC를 정상·실패·경계 상황에 적용하면 여러 TC가 생길 수 있다.

| AC | TC의 예시 |
| --- | --- |
| 동일 주문은 한 번만 결제된다 | 동일 주문·멱등 키로 두 번 요청해 차감은 하나이고 기존 결과가 반환되는지 확인 |
| 잔액 부족 결제는 성공하지 않는다 | 잔액 1,000에서 1,500 결제를 요청해 실패하고 잔액·원장이 유지되는지 확인 |
| 허용되지 않은 음수 잔액이 발생하지 않는다 | 잔액 1,000에서 서로 다른 주문의 800 결제를 동시에 요청해 최대 하나만 성공하는지 확인 |

이 표는 음수 잔액을 허용하지 않는 정책의 예시다. 실제 정책으로 기대값을 확정해야 한다. 배열 검색이라면 빈 배열, 한 원소, 중복 원소가 각각 다른 경계를 드러낸다. 첫 위치를 반환한다는 계약은 중복 입력에서도 유지되어야 한다.

## AI를 활용할 때

도메인 용어·정책·불변식 → 스펙 → AC/TC → 테스트 → 구현 → 리뷰 순서로 기준을 연결한다. 이는 활용 가능한 작업 방식이며 모든 개발에 강제되는 절차는 아니다. TDD를 적용할 때는 구현 전 테스트가 의도한 이유로 실패하는지 확인하고 최소 구현 뒤 리팩터링한다. AI가 테스트와 구현을 함께 작성하면 같은 오해를 공유할 수 있으므로 사람이 기대값과 테스트 변경을 별도로 검토한다.

## 주의점

내부 Repository 메서드 이름보다 관찰 가능한 결과를 우선한다. 시간·난수·외부 응답을 통제하고 테스트 간 실행 순서 의존을 없앤다. 같은 결과 집합을 대표하는 동치 클래스와 경계값을 선택하며, API당 테스트 개수를 고정하지 않는다.

## 꼬리질문

1. AC와 TC를 구분하면 요구사항과 검증 절차 사이에 어떤 연결이 생기는가?
2. 잔액 1,000에서 800 결제 두 건이 겹칠 때 중복 요청 TC와 서로 다른 주문의 동시성 TC는 어떻게 다른가?
3. AI가 테스트도 고칠 수 있다면 요구사항이 잘못 완화되는 것을 어떤 리뷰 기준으로 발견할까?
