# 롤링 배포의 API 호환성과 WebSocket 복구

> 신·구 클라이언트와 서버가 공존하는 동안 계약을 유지하고, 연결이 끊겨도 저장된 상태로 업무를 복구한다.

- **전제:** N-1과 N은 배포 도중뿐 아니라 브라우저 캐시·열린 탭·이벤트 보존 기간에도 공존할 수 있다.
- **원리:** 호환 서버를 먼저 준비하고 새 기능을 나중에 활성화하며, 재접속 뒤 누락 상태를 동기화한다.
- **주의:** 필드 추가, 정적 파일 전환, 요청 식별자만으로 호환성·롤백·멱등성이 자동 보장되지는 않는다.

## N-1과 N의 계약

롤링 중에는 이전 API와 새 API가 동시에 요청을 받는다. 배포 전에는 다음 조합을 검증한다.

| 조합 | 확인할 내용 |
| --- | --- |
| 구 클라이언트 → 새 API | 기존 필드·오류·인증 동작 유지 |
| 새 클라이언트 → 구 API | 공존·롤백 중 새 요청을 거부하지 않는지, 기능 비활성화로 회피 가능한지 |
| 새 소비자 → 과거 이벤트 | 이전 payload·누락 필드를 처리하는지 |
| 구 소비자 → 새 이벤트 | 롤백 후에도 처리 가능한지, 구 형식 경로를 유지해야 하는지 |

이 사례에서는 `/api/v1`에 기존 계약을 깨지 않는 선택적 확장을 우선하고, 필드 삭제·이름·의미 변경은 `/api/v2` 같은 새 계약으로 분리한다. 다만 **추가 변경도 클라이언트의 파싱·enum 처리·필수값 규칙에 따라 깨질 수 있으므로 테스트가 필요하다**.

제공된 기록상 요청 모델은 `extra="forbid"`다. 이 설정은 선언하지 않은 입력을 거부하므로 새 필드를 보내는 프론트를 먼저 공개하면 이전 API에서 검증 오류가 난다. FastAPI 기본 검증 처리에서는 422 응답이 될 수 있다. [Pydantic의 extra 설정](https://docs.pydantic.dev/latest/api/config/#pydantic.config.ConfigDict.extra)과 [FastAPI 검증 오류 처리](https://fastapi.tiangolo.com/tutorial/handling-errors/#override-request-validation-exceptions)로 확인할 수 있다.

안전한 선택은 **필드를 읽을 수 있는 API를 한 릴리스 먼저 배포**하거나, **API 롤링 완료를 확인한 뒤 프론트의 새 기능을 활성화**하는 것이다. 후자는 구 API로 롤백할 때의 추가 대책까지 마련해야 한다.

## 유지할 계약

- 이 사례의 오류 구조 `{error:{code,message,retryable}}`를 유지한다. 특정 서비스의 계약이며 모든 API의 표준 오류 형태라는 뜻은 아니다.
- JWT·쿠키·세션은 공존 기간에 양쪽 서버가 해석할 수 있어야 한다. 서명 검증과 필수 claim도 계약에 포함한다.
- 변경 요청에는 `request_id` 또는 `Idempotency-Key`를 사용할 수 있지만, **서버가 같은 키의 처리 상태·결과를 저장하고 중복 실행을 막아야** 한다. 추적 ID를 붙이는 것만으로 멱등성이 생기지 않는다. [멱등 키와 재시도](../idempotency/idempotency-key.md)를 함께 확인한다.

## 프론트엔드 전환과 열린 탭

버전별 정적 파일을 먼저 게시하고 API 준비가 끝난 뒤 `index.html`을 원자적으로 전환한다. 이전 파일은 롤백과 이전 페이지의 지연 로딩을 위해 유지한다. HTML 재검증 정책과 해시가 포함된 정적 파일의 장기 캐시를 구분한다.

Web Pod가 여러 개이면 **모든 경로에서 새 HTML이 참조하는 정적 파일을 제공할 수 있어야** 한다. 파일시스템 한 곳의 원자적 전환만으로 여러 Pod·CDN·캐시가 동시에 바뀌지는 않는다.

이전 `index.html`을 복구해도 이미 열린 탭에서 실행 중인 새 JavaScript가 이전 버전으로 바뀌지는 않는다. 따라서 다음 롤백 순서는 호환성 확인을 전제로 한다.

```text
새 기능 비활성화 · 이전 index.html 복구
  → 실행 중인 신버전 클라이언트와 호환 확인
  → API 이전 digest로 복구
  → 남아 있는 새 이벤트와 호환 확인
  → Worker 이전 digest로 복구
  → 확장된 DB 스키마 유지 · 업무 흐름 재검사
```

기능 플래그·재로드 안내·호환 API 유지 중 적합한 대책을 마련한다. 플래그도 구·신 클라이언트가 실제로 따르는지 확인해야 한다.

## WebSocket은 연결 유지보다 상태 복구

Pod 종료 시 기존 WebSocket은 끊길 수 있다. Kubernetes가 소켓을 새 Pod로 옮겨 주지 않는다. 제공된 운영 기록에는 재접속 후 `sync`로 메시지와 생성 chunk를 복구하는 경로가 있으나, 이 구현의 보장 범위는 이번 문서에서 재점검하지 않았다.

복구 설계는 다음 조건으로 검증한다.

1. 끊김을 감지하면 backoff와 무작위 지연을 두어 재접속한다.
2. 재인증 후 마지막으로 확정한 메시지 ID·순번·cursor를 기준으로 `sync`한다.
3. 서버가 보존한 메시지·chunk를 재조회하고 중복 이벤트를 제거한다.
4. 보존 기간 밖이거나 chunk가 저장되지 않았다면 전체 상태 재조회 등 fallback을 정한다.

메시지 타입·payload도 양방향 호환성을 검증한다. **“재접속 성공”과 “누락 없이 업무 복구”는 다른 성공 조건**이다. 로그인·대화 조회·인증된 연결·전송·강제 재접속·sync를 하나의 합성 검사로 확인한다.

## 주의점

N-1 호환은 최소 출발점이다. 오래 열린 탭과 보존된 이벤트가 있다면 지원 기간을 더 길게 잡아야 한다. 연결 복구는 애플리케이션의 저장·재생·중복 제거 설계에 달려 있고, 데이터 계층 장애에 대한 HA를 대신하지 않는다.

## 꼬리질문

1. 선택적 필드를 추가했는데도 구버전 클라이언트나 서버가 실패할 수 있는 이유는 무엇인가?
2. 새 프론트를 공개한 뒤 API를 롤백해야 한다면 열린 탭과 새 요청을 어떻게 처리할까?
3. WebSocket 재접속 후 sync가 성공해도 누락 없는 복구를 보장하려면 어떤 보존·순서·중복 제거 조건이 필요한가?
