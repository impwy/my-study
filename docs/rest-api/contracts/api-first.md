# API First와 명세의 역할

> 구현 전에 외부 인터페이스 계약을 합의하면 프론트와 백엔드가 같은 기대 동작을 기준으로 개발할 수 있다.

- 제품 요구·동작 명세·API 계약은 목적과 범위가 다르다.
- 경로·입력·응답·오류·인증·페이징·멱등성을 먼저 합의한다.
- Swagger UI와 실제 응답 모킹을 구분한다.

## 설명

PRD(Product Requirements Document)는 제품이 해결할 문제와 요구 맥락을 담는다. 요구사항 명세는 동작과 제약을, API 명세는 외부 인터페이스 계약을 구체화한다. 조직이 이름을 섞어 쓰더라도 문서가 답해야 할 질문은 구분한다.

API First는 컨트롤러를 먼저 작성하는 특정 순서에 한정되지 않는다. 사용자 흐름·정책·예외를 확인하고 요청·응답·오류를 합의한 뒤 그 계약으로 각 부분을 구현한다. OpenAPI는 HTTP API를 기계와 사람이 읽을 수 있도록 기술하는 표준이다.

```text
제품 요구·정책 → API 계약 합의 → 예시·모킹 제공
                                → 프론트·백엔드 구현 → 통합 검증
```

계약에는 필수·선택 값, 오류 구조, 인증, 정렬·페이징, 벌크 한도와 재시도 정책도 포함한다. BFF(Backend for Frontend)는 특정 프론트의 요구에 맞춘 백엔드라는 뜻이며 API 명세나 모킹 도구의 이름이 아니다.

## 주의점

Swagger UI는 API 문서를 표시하고 호출을 시험하는 도구다. 문서만 제공했다고 모킹 서버가 생기는 것은 아니다. 예시 응답과 실제로 응답을 돌려주는 스텁·모킹을 구분한다. 계약이 바뀌면 명세·예시·양쪽 구현과 통합 검증을 함께 갱신한다. 회의 시간이나 문서 개수보다 계약의 모호함을 줄였는지가 중요하다.

## 꼬리질문

1. 제품 요구와 API 계약을 구분하면 어떤 누락과 구현 불일치를 줄일 수 있는가?
2. 백엔드 완성 전 프론트가 결제 실패 화면을 개발하려면 어떤 오류 계약과 모킹이 필요한가?
3. 문서의 요청·응답과 실제 구현이 달라지는 것을 어떻게 발견하고 변경을 전파할까?

## 참고 자료

- [OpenAPI Specification](https://spec.openapis.org/oas/latest.html) — 경로·스키마·응답·보안·예시를 기술하는 표준을 확인한다.
- [Swagger UI](https://swagger.io/open-source/swagger-ui/) — 문서 표시와 상호작용 도구의 역할을 확인한다.
- [Microsoft · Backends for Frontends](https://learn.microsoft.com/en-us/azure/architecture/patterns/backends-for-frontends) — 특정 클라이언트 요구에 맞춘 백엔드 경계를 확인한다.
