# 멱등 키와 요청 재시도

> 같은 요청의 중복 효과는 멱등성으로 막고 서로 다른 요청의 자원 경쟁은 별도 동시성 제어로 보호한다.

- 타임아웃은 외부 작업의 실패 확정이 아니다.
- 업무 효과와 요청 식별·결과 기록을 함께 보호한다.
- 멱등성은 서로 다른 주문의 동시 차감을 해결하지 않는다.

## 설명

클라이언트가 결제 응답을 받지 못했어도 서버는 이미 처리했을 수 있다. 업무 범위 안에서 요청의 정체성을 멱등 키로 식별하고 처리 중·완료 상태와 결과를 저장한다. 같은 키의 재요청에는 계약에 맞는 결과를 돌려주고 다른 본문이면 충돌 정책을 적용한다. DB의 유일성 제약과 업무 변경을 가능한 한 같은 트랜잭션으로 보호한다.

| 상황 | 필요한 보호 |
| --- | --- |
| 동일 주문을 다시 요청 | 멱등 키·업무 식별자·결과 보존 |
| 서로 다른 주문이 같은 잔액을 사용 | 조건부 갱신 또는 요구에 맞는 락 |
| PG 응답 유실 | PG의 멱등성·상태 조회·통지·대사 |

음수 잔액을 허용하지 않는 정책에서 잔액 1,000에 800 결제 두 건이 겹치면 최대 하나만 성공해야 한다. 두 건은 서로 다른 요청이므로 멱등 키만으로는 부족하다. InnoDB의 잠금 읽기 등으로 읽기·변경 경계를 보호하거나 조건부 갱신의 결과를 확인한다.

## 주의점

외부 PG와 로컬 DB가 자동으로 하나의 ACID 트랜잭션이 되는 것은 아니다. 외부 성공 뒤 내부 저장 실패를 복구할 상태 전이와 재처리 절차가 필요하다. 멱등 키의 범위·만료·동시 처리·본문 일치 정책은 서비스별로 정한다. Kafka 프로듀서의 멱등성도 결제 업무 중복 방지와는 범위가 다르다. 원장·잔액·환불 누계의 불변식을 별도로 정의하며 테이블을 합치는 것만으로 정합성이 보장되지 않는다.

1. 응답 유실 후 재시도가 중복 효과를 만들 수 있는 이유는?
2. 동일 주문 재시도와 서로 다른 주문의 동시 차감을 각각 어떤 식별자와 자원 경계로 보호할까?
3. 멱등 기록이 만료되거나 PG 성공 직후 DB 저장이 실패하면 어떤 조회·대사·복구 정책이 필요할까?
