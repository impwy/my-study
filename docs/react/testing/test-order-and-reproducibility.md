# 테스트 순서 의존과 seed 재현

> 순서를 바꿀 때 깨지는 테스트는 seed로 재현을 고정하고 선행 테스트와 공유 상태를 좁혀 원인을 찾는다.

- **단서:** 단독 실행은 통과해도 앞선 테스트의 상태·작업에 영향을 받을 수 있다.
- **재현:** seed와 함께 실행 범위·버전·설정을 기록한다.
- **검증:** 실패 테스트의 단언을 완화하기 전에 상태를 남긴 테스트를 찾는다.

## 설명

테스트 A가 남긴 상태 때문에 B가 실패하면 B만 실행해서는 문제가 보이지 않는다. 실행 순서를 섞는 검사는 평소 순서가 숨기던 의존을 드러낸다. 다만 순서 변경은 타이밍도 바꾸므로, 셔플 실패만으로 상태 누수를 확정하지는 않는다.

| 확인 | 얻는 단서 |
| --- | --- |
| 같은 실행 범위·seed로 반복 | 매번 같은 순서에서 실패하는지, 간헐적 타이밍 문제인지 구분 |
| 실패 파일만 실행 | 같은 파일 안에서 재현되는지 확인 |
| A → B, B → A를 비교 | 실패에 필요한 선행 테스트를 좁힘 |
| C → B와 비교 | A에만 있는 스토어·타이머·요청을 찾음 |
| 의심 상태 하나만 초기화 | 원인 가설을 검증 |

여러 선행 테스트의 조합이 필요할 수도 있다. 쌍으로 재현되지 않으면 실패 전 구간을 반씩 줄여 최소 조합을 찾는다. 찾은 테스트는 [전역 상태](global-store-and-timer-isolation.md), [비동기 완료 조건](async-ui-completion.md), [네트워크 모킹의 정리 범위](msw-handler-and-fixture-isolation.md)를 확인한다.

## 실행 예제

설치된 Vitest로 실행한다. 아래 파일 경로는 조사할 테스트 파일로 바꾼다.

```bash
# 파일과 테스트 순서를 섞고 재현 seed를 고정한다.
npx vitest run --sequence.shuffle --sequence.seed=7

# 같은 seed라도 파일을 줄이면 원래 전체 실행 순서와 달라질 수 있다.
npx vitest run src/flow.test.tsx --sequence.shuffle --sequence.seed=7

# 첫 실패에서 종료 코드를 유지한다.
for seed in 1 2 3 4 5; do
  npx vitest run --sequence.shuffle --sequence.seed="$seed" || exit "$?"
done
```

## 주의점

seed는 **셔플의 난수 입력**이다. 네트워크 지연·현재 시각·워커 스케줄링까지 고정하지 않는다. 코드·테스트 목록·버전·설정이 달라지면 같은 숫자라도 동일한 재현을 보장하지 않는다.

일반 테스트는 파일 안에서 선언 순서로 실행되지만 `concurrent` 등은 별도다. 파일 실행 순서는 캐시·병렬 실행 등의 영향을 받으므로 모든 파일이 작성 순서대로 돈다고 가정하지 않는다. 기본 파일 격리도 같은 파일의 개별 테스트마다 전역 스토어를 새로 만들지는 않는다. 여러 seed 통과는 검사한 범위의 증거이며 독립성의 증명은 아니다. 한 원인을 고친 뒤 다른 테스트가 실패할 수 있으므로 실패별 원인과 검증 범위를 나눠 기록한다.

## 꼬리질문

1. B가 단독으로는 통과하고 A → B에서만 실패한다면 어떤 자원의 수명을 먼저 조사할까?
2. 두 테스트로 줄였더니 재현되지 않을 때 선행 테스트의 조합과 실행 타이밍을 어떻게 구분할까?
3. 동일 seed가 CI와 로컬에서 다르게 실패한다면 seed 외에 어떤 환경·설정을 기록해야 할까?
