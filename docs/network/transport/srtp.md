# SRTP: 실시간 통화 미디어 보호하기

> SRTP는 RTP 미디어에 기밀성·메시지 인증·재전송 공격 방지 기능을 제공하며, 통화 제어 신호의 TLS 보호와는 적용 구간이 다르다.

- **역할:** SRTP는 Secure Real-time Transport Protocol로, RTP의 보안 프로파일이다.
- **원리:** 협의된 키와 보안 설정으로 미디어를 암호화·인증하고 재전송 공격을 탐지한다.
- **주의:** SRTP 사용 여부만으로 전체 통화 경로의 종단 간 암호화를 단정할 수 없다.

## 설명

기본 [RTP](rtp.md)는 미디어 패킷의 전송·재생 정보를 제공하지만 그 자체로 음성 내용을 암호화하지 않는다. SRTP는 실시간 통화에 맞춰 이 미디어를 보호한다.

| 보호 기능 | 다루는 문제 |
| --- | --- |
| 기밀성 | 패킷을 관찰한 제삼자가 음성 내용을 읽는 문제 |
| 메시지 인증·무결성 | 패킷 위조나 변조를 수신 측이 구분하는 문제 |
| 재전송 공격 방지 | 과거의 유효한 패킷을 다시 보내 수신 측을 속이는 문제 |

실제 적용되는 보호는 협의한 암호·인증 설정에 따라 달라진다. 수신 측은 패킷 인덱스와 재전송 검사 상태 등을 이용해 수용할 패킷을 판단한다. RTCP 제어 트래픽에 대응하는 보호 방식은 SRTCP이다.

키를 합의하고 관리하는 절차는 SRTP 외부의 메커니즘이 담당한다. WebRTC에서는 DTLS-SRTP로 키를 설정하고 SRTP로 미디어를 전송한다. DTLS가 음성 패킷 전부를 직접 운반한다는 의미는 아니다.

[SIP](sip.md)를 TLS로 보호하는 것은 통화 설정·종료 신호를 보호하는 일이다. SRTP는 실제 음성 경로를 보호하므로 두 설정을 따로 확인한다. 전화 사업자나 미디어 게이트웨이가 연결을 종단하고 새로운 연결로 이어주면 각 구간의 보호 경계도 달라진다.

## 주의점

- 재전송 공격 방지는 네트워크 손실 패킷을 복구하는 기능이 아니다. SRTP는 음질·지연·전달 성공을 보장하지 않는다.
- “SRTP 사용”이라는 정보만으로 모든 구간에서 암호화가 켜져 있는지, 중간 사업자가 복호화할 수 없는지까지 알 수는 없다.
- [AI 전화 상담](ai-call-voice-pipeline.md)에서 모델이 음성을 처리하려면 해당 처리 지점은 음성 내용에 접근한다. SRTP는 그 처리 지점까지의 전송 보호와 구분해서 이해한다.

## 꼬리질문

1. RTP에 SRTP를 적용하면 어떤 위협을 줄일 수 있으며, 키 설정이 별도 메커니즘으로 필요한 이유는 무엇인가?
2. SIP 신호는 TLS로 보호하지만 음성은 기본 RTP로 보내는 고객센터에서, 음성 기밀성을 확보하려면 무엇을 바꿔야 하는가?
3. 전화 사업자·게이트웨이·AI 서비스가 각각 SRTP를 종단한다면, 전체 통화가 종단 간 암호화됐다고 말할 수 있는 조건은 무엇인가?
