# RTP: 실시간 음성의 순서와 재생 시점을 전달하기

> RTP는 음성·영상 패킷에 순서 번호와 타임스탬프 등을 붙여 수신 측의 실시간 재생을 돕지만, 전달 성공이나 지연을 보장하지 않는다.

- **역할:** RTP는 Real-time Transport Protocol로, 실시간 미디어의 전송 정보를 정의한다.
- **원리:** Sequence number는 패킷 순서·누락 파악에, timestamp는 미디어 재생 시점 복원에 사용한다.
- **주의:** RTP는 코덱·신뢰성 보장·암호화와 구분해야 한다.

## 설명

통화 음성은 작은 구간으로 나누고 코덱으로 표현한 뒤 패킷으로 전송한다. RTP 헤더는 수신 측이 미디어를 구분하고 재생하는 데 필요한 정보를 제공한다.

| 정보 | 의미 |
| --- | --- |
| Sequence number | 전송한 패킷의 순서를 식별하는 번호 |
| Timestamp | 해당 미디어 데이터의 샘플링 시점을 코덱 등의 클록 기준으로 표현한 값 |
| Payload type | 협의된 미디어 형식·페이로드 해석 방법을 식별하는 값 |
| SSRC | RTP 동기화 소스를 식별하는 값 |

패킷이 `101 → 103 → 102` 순서로 도착하면 수신 측은 번호로 순서 뒤바뀜을 파악할 수 있다. 재생 기한까지 도착하지 않은 패킷은 손실로 취급해 코덱의 손실 보정 등으로 처리할 수 있다. **번호가 있다는 사실이 재전송이나 복구를 보장하지는 않는다.**

수신 측은 도착 간격의 흔들림을 완화하도록 재생 버퍼를 둘 수 있다. 많이 기다리면 늦은 패킷을 수용하기 쉽지만 통화 지연도 늘어난다. 함께 사용하는 RTCP는 손실률·지터 같은 전달 상태를 보고하는 데 쓰인다.

RTP는 흔히 UDP 위에서 사용하지만 기반 전송 계층과 독립적으로 설계됐다. [TCP·UDP의 특성](tcp-and-udp.md), 통화 제어를 담당하는 [SIP](sip.md), 미디어를 보호하는 [SRTP](srtp.md)를 구분해서 이해한다. WebRTC 미디어 전송은 보호된 RTP를 사용한다.

## 주의점

- RTP 자체는 전송 성공, 순서대로 도착, 일정한 지연, 대역폭을 보장하지 않는다.
- Timestamp는 일반적으로 밀리초나 현재 시각을 그대로 기록한 값이 아니다. 클록 기준과 상대 차이를 함께 해석한다.
- RTP는 음성을 압축하는 코덱이 아니다. Opus·G.711 등으로 표현한 미디어를 운반하는 형식이며, 기본 RTP 자체에 암호화는 없다.

## 꼬리질문

1. 순서 번호와 타임스탬프가 모두 필요한 이유는 무엇이며, 각각 패킷 순서와 미디어 재생에서 어떤 문제를 해결하는가?
2. AI 상담 음성의 패킷이 순서가 바뀌거나 늦게 도착할 때, 수신 측은 재생 버퍼와 손실 처리를 어떻게 활용할 수 있는가?
3. 손실된 음성을 모두 기다리는 방식이 대화에는 불리할 수 있는 이유는 무엇이며, 버퍼를 키울 때 어떤 조건을 고려해야 하는가?
