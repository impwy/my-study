# WebRTC 음성대화의 연결과 턴 처리

> WebRTC 연결을 유지하는 것과 사용자의 새 발화를 확정하고 이전 답변을 안전하게 중단하는 것은 서로 다른 책임이다.

- **전송:** 같은 연결의 마이크·출력 트랙으로 여러 턴을 주고받는다.
- **턴 확정:** VAD의 소리 감지와 STT의 실제 단어 인식을 구분한다.
- **검증:** 패킷 수신뿐 아니라 정정된 주제·실제 재생 음성·종료 상태를 확인한다.

## 설명

학습 질문: “WebRTC로 통화는 연결됐는데 왜 답변이 중지되거나 대화가 이어지지 않을까?”

[STT → LLM → TTS 파이프라인](ai-call-voice-pipeline.md)에서는 음성을 텍스트로 인식하고 답변을 생성한 뒤 다시 음성으로 합성한다. WebRTC는 이 입력·출력 음성을 전달하는 통로다. 같은 PeerConnection을 유지해도 발화 인식·문맥·생성 취소가 잘못되면 대화는 끊긴다.

VAD는 발화의 시작·끝 후보를 찾는다. 소리가 시작됐다는 결과만으로 기존 생성을 취소하면, 실제 단어가 없는 잡음에도 빈 ‘생성 중지’ 답변이 남을 수 있다. 재생 일시 정지와 생성 취소를 나누는 방법이 있다.

```text
VAD 시작 → 재생 일시 정지·버퍼 보존
발화 종료 → STT
  말이 확인됨 → 이전 생성·합성 취소 → 버퍼 폐기 → 새 턴 접수
  빈 인식임   → 기존 버퍼 재생 재개
```

명시적 중단 버튼은 즉시 취소할 수 있다. 새 턴으로 넘어갈 때는 모델 작업뿐 아니라 합성 HTTP 스트림, 대기 큐, 미재생 음성도 함께 정리해야 한다. 이전 요청의 늦은 결과가 새 답변에 섞이지 않도록 세대 번호 같은 경계를 둔다.

## 스트리밍과 지연

TTS 응답을 조금씩 받아 재생하면 전체 파일이 완성되기 전에 소리를 낼 수 있다. 그러나 TTS의 첫 오디오 시간은 발화 종료 판단·STT·LLM 생성·네트워크·재생 대기를 포함한 전체 응답 시간이 아니다. 네트워크 청크 경계가 WAV 헤더나 PCM 샘플 경계와 같다고 가정해서도 안 된다.

## 검증과 주의점

- 같은 질문 반복에 더해 ‘이름 소개 → 이름 재질문 → 이름 정정 → 새 이름과 주제 재질문’을 검사한다. 연결·트랙 유지, 저장 건수, 답변 내용, 종료 자원 정리를 함께 본다.
- 수신 RTP 에너지는 음성이 있다는 증거이지 올바른 한국어 답변이라는 증거는 아니다. 합성 테스트 입력의 원격 응답을 캡처해 재인식하는 방법으로 내용도 점검할 수 있다.
- 정지 중 버퍼도 상한과 백프레셔가 필요하다. VAD·STT가 잡음이나 에코를 단어로 오인하는 경우는 별도 평가해야 한다.
- 합성 입력의 성공을 사람의 마이크·주변 소음·외부 TURN·장시간 통화의 성공으로 일반화하지 않는다.

## 꼬리질문

1. WebRTC 연결 상태가 정상이어도 음성대화가 이어지지 않을 수 있는 이유는 무엇인가?
2. AI가 말하는 중 짧은 소리가 들렸다면 언제 재생을 멈추고 언제 생성 작업을 취소해야 하는가?
3. 버퍼를 보존한 채 정지하는 방식에서 메모리 상한·에코·잘못된 STT 결과는 어떻게 검증해야 하는가?
