# 배치와 스트림 처리

> 배치는 유한한 묶음을, 스트림은 지속되는 입력을 처리하며 Kafka 직접 수신과 처리 상태의 복구를 구분한다.

- 배치는 묶음의 완료·커밋·재시작 경계를 정한다.
- Flink는 스트림 처리 엔진이고 Kafka는 이벤트 로그를 저장·전달한다.
- 중간 저장소를 생략해도 처리 위치·상태·출력의 복구 설계는 필요하다.

## 설명

Spring Batch의 chunk 방식은 일정 입력을 읽고 변환·기록한 뒤 커밋하며 재시작에 필요한 상태를 관리할 수 있다. 스트림은 계속 도착하는 이벤트의 위치·지연·실패를 추적한다. 선택 기준은 필요한 최신성·처리량·정확성·운영 비용이다.

Apache Flink는 상태를 가진 계산·집계 등을 수행하는 처리 엔진이다. Kafka 커넥터의 소스로 Kafka 이벤트를 직접 읽을 수 있다. “중간 저장소 없이 Kafka에서 바로 수신”은 별도 DB나 파일로 먼저 옮기지 않는 입력 경로로 이해한다. 이 메모만으로 실제 처리기·출력 대상·보장 수준까지 확정할 수는 없다.

```text
이벤트 생산 → Kafka → Flink 처리 → 출력 대상
                         ↘ 체크포인트로 처리 상태 복구
```

체크포인트는 입력 위치와 연산 상태를 복구하는 데 사용된다. 외부 출력까지 일관되게 복구되는지는 싱크의 트랜잭션·멱등성 지원과 설정에 달려 있다. Kafka 자체도 보존 저장소이고 상태 저장·체크포인트 역시 저장을 사용할 수 있으므로 “저장이 전혀 없다”는 뜻은 아니다.

## 주의점

이벤트 `(A,+2)·(A,+2)·(B,+3)`에서 A가 같은 사건의 재전달이라면 중복을 제외한 합은 5다. 이벤트 식별과 재처리 계약이 없으면 다시 합산할 수 있다. 스트림 결과를 배치로 대사할 때 지연·누락·정정 이벤트를 구분한다. chunk 크기를 늘리는 것만으로 성능이 항상 좋아지거나 외부 Writer 효과가 DB 트랜잭션에 포함되지는 않는다.

## 꼬리질문

1. 배치와 스트림은 입력의 끝과 진행 상태를 어떻게 다르게 다루는가?
2. Flink가 Kafka를 직접 읽다 재시작되면 입력 위치·연산 상태·출력 효과를 어떻게 맞춰야 할까?
3. 싱크가 트랜잭션이나 멱등성을 지원하지 않으면 체크포인트만으로 어떤 중복을 막지 못할까?
