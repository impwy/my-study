# 폴백과 장애 복구의 경계

> 주 경로 실패 때 대체 동작을 선택하되 부하·데이터 정확성·복구 절차를 함께 검증한다.

- 폴백은 주 기능 실패 시 선택하는 대체 동작이다.
- 폴백·재시도·장애 전환·서킷 브레이커는 역할이 다르다.
- 드물게 실행되는 대체 경로도 실패와 과부하를 시험해야 한다.

## 설명

Fallback(폴백)은 원래 경로가 실패하거나 사용할 수 없을 때 대체 결과·기능을 제공하는 방식이다. 추천 서비스가 실패하면 기본 목록을 보여 주는 것이 예다. 금액 확인처럼 정확성이 필수인 기능에서 임의 값을 반환하는 것은 같은 선택으로 취급할 수 없다.

| 용어 | 주요 역할 |
| --- | --- |
| 재시도 | 같은 작업을 다시 시도 |
| 폴백 | 대체 결과·동작 선택 |
| 장애 전환 | 다른 인스턴스·복제본 등으로 역할 이동 |
| 서킷 브레이커 | 반복 실패 경로의 호출을 일시 제한하고 회복 확인 |

이 기능들은 함께 사용될 수 있다. 원본 DB가 느릴 때 캐시를 사용하는 설계라면 허용할 오래된 값의 범위가 필요하다. 반대로 캐시 장애 때 모든 요청을 DB로 보내면 DB도 과부하될 수 있다. 대체 경로가 정상 시 부하와 같은 용량을 갖는지 확인한다.

## 주의점

폴백을 추가하면 정상 경로와 장애 경로 사이의 코드·상태 차이가 늘어난다. 주 경로 실패, 폴백 실패, 동시 과부하, 정상 복귀를 구분해 검증한다. 조회 기능을 축소할 수 있는 조건과 결제·잔액 등 정확성 때문에 실패를 명확히 반환해야 하는 조건을 정책으로 정한다. 재시도가 있는 쓰기는 [멱등 키](../../rest-api/idempotency/idempotency-key.md)와 함께 검토한다. “폴백 시스템”이라는 메모만으로 실제 대체 대상이나 구현을 확정하지 않는다.

## 꼬리질문

1. 폴백이 재시도나 장애 전환과 다른 이유는?
2. 캐시 장애 때 요청을 DB로 우회하면 어떤 부하·응답 정책을 확인해야 할까?
3. 추천 목록에는 기본값을 줄 수 있어도 결제 잔액에는 같은 방식이 어려운 이유는 무엇인가?
