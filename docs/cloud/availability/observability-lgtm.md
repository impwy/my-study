# Observability와 LGTM·Datadog

> 메트릭·로그·트레이스를 연결해 내부 상태를 추론하고 Grafana 도구 조합과 Datadog 통합 서비스를 구분한다.

- 메트릭은 수치, 로그는 사건 기록, 트레이스는 요청의 경로와 시간을 나타낸다.
- LGTM은 Loki·Grafana·Tempo·Mimir이며 M은 Prometheus가 아니다.
- 변경 이력은 원인 후보를 좁히는 맥락이며 장애 원인의 증명은 아니다.

## 설명

Observability(관측 가능성)는 시스템이 내보내는 데이터로 내부 상태를 파악할 수 있는 능력이다. 메트릭은 오류율·지연 같은 수치의 추세를, 로그는 실패 사건을, 트레이스는 여러 서비스에 걸친 요청 경로와 구간 시간을 보여 준다.

| 도구 | 역할 |
| --- | --- |
| Prometheus | 메트릭 수집·저장·조회와 알람 규칙 평가 |
| Loki | 로그 저장·조회 |
| Grafana | 데이터 소스 연결·시각화·알람 |
| Tempo | 분산 트레이스 저장·조회 |
| Mimir | 대규모 메트릭 저장·조회 |
| Datadog | 메트릭·로그·트레이스·성능 분석 등을 제공하는 상용 관측 플랫폼 |

Prometheus로 수집한 메트릭을 Mimir에 보내 보관하고 Grafana에서 조회하는 구성이 가능하다. LGTM 도구를 직접 조합할 수도 있고 관리형 Grafana Cloud를 사용할 수도 있다. Datadog은 통합 서비스이지만 실제 기능 범위·데이터 수집 방식은 구성에 맞춰 확인한다.

## 적용 예시와 주의점

“변경 이력을 이슈 알람에 함께 제공”한다면 알람에 발생 시각·환경·서비스·배포 버전과 변경 기록 링크, 관련 대시보드·로그·트레이스를 연결한다. 이는 설계 예시다. 배포 직후 오류가 늘었다는 시간적 상관만으로 해당 변경이 원인이라고 확정하지 않는다. 수집 누락·보존 기간·비용을 확인하고 세 종류의 데이터가 같은 사건을 가리키도록 식별 맥락을 맞춘다.

## 꼬리질문

1. 메트릭·로그·트레이스는 같은 장애를 각각 어떤 관점에서 보여 주는가?
2. 배포 직후 오류율이 상승했을 때 변경 이력과 어떤 로그·트레이스를 알람에서 연결하면 좋을까?
3. 변경 시점과 장애 시점이 가깝더라도 원인으로 단정할 수 없는 이유와 추가 확인은 무엇인가?
