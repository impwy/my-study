# GitHub Flow와 리뷰할 변경 단위

> 짧은 작업 브랜치와 PR로 변경을 검토하고 main에 통합하며 상시 develop은 팀의 별도 운영 선택이다.

- 작업 브랜치 → 변경·커밋 → PR → 리뷰·검증 → 병합 → 브랜치 정리로 진행한다.
- PR은 해결한 문제·설계 판단·검증 결과를 연결한다.
- main/dev/feature 운영안을 공식 GitHub Flow의 필수 구성으로 설명하지 않는다.

## 설명

GitHub Flow는 가벼운 브랜치 기반 협업 흐름이다. 기본 브랜치에서 작업 브랜치를 만들고 변경을 커밋·푸시한다. 준비된 변경은 PR로 피드백을 받고 필요한 수정과 검증 뒤 병합한다. draft PR로 이른 피드백을 받을 수도 있다.

PR에는 구현한 기능만 쓰지 않고 문제, 변경 후 동작, 주요 판단, 검증 결과와 리뷰가 필요한 지점을 적는다. 예를 들어 동일 결제 키 재요청과 서로 다른 주문의 동시 차감을 구분해 확인했다면 그 두 시나리오와 트랜잭션·실패 복구의 경계를 설명한다. 실제 수행하지 않은 검증을 했다고 적지 않는다.

## 주의점

상시 develop 브랜치는 공식 GitHub Flow의 필수 요소가 아니다. 추가 브랜치는 배포·통합 요구에 맞춘 팀의 선택으로 설명한다. unrelated 변경을 한 PR에 묶으면 문제와 검증 근거가 흐려진다. 리뷰 기록·작은 변경·실패 해결 근거가 기술 이름이나 문서 개수보다 판단을 평가하는 데 도움이 된다. 일정과 병합 승인 조건은 저장소와 팀의 합의로 확인한다.

## 꼬리질문

1. 작업 브랜치와 PR이 변경 검토·복구에 도움이 되는 이유는?
2. 결제 PR에서 중복 요청과 동시 차감 검증을 리뷰어가 이해하도록 어떤 근거를 함께 적을까?
3. 상시 develop이 필요해지는 배포 요구가 있다면 기본 흐름의 어떤 비용과 이득이 달라질까?
